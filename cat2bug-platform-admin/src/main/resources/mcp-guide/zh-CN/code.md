## 代码模块是什么

项目可以在平台上托管多个 Git 仓库。代码模块让你在线浏览、搜索代码和查看提交，并在修复缺陷时关联提交、创建合并请求（PR）。

## 常用操作

| 目的 | 工具 |
|---|---|
| 列出本项目仓库 | `list_repositories`（`get_current_project` 也会返回） |
| 本地仓库对应哪个平台仓库 | `resolve_project_by_git_remote`（传 `git remote get-url origin` 的结果） |
| 浏览目录 / 读文件 | `list_code_tree`、`read_code_file` |
| 搜索代码 | `search_code` |
| 查提交 | `list_commits`、`get_commit` |
| 创建 / 查看 PR | `describe_operation` / `call_operation` → `gitPullRequest.create` 等 |

## 缺陷对应哪个源码仓库

一次 MCP 授权只绑定**一个 Cat2Bug 项目**，但该项目下可以有多个 Git 仓库。缺陷本身不绑定仓库。先用 `get_current_project` 或 `list_repositories` 拿到仓库列表（含 `defaultBranch`）；本地有工作区时再对 `origin` 调 `resolve_project_by_git_remote`。

### 仓库确认（少打断）

- **不问仓库**：本项目恰好**一个**源码仓库，且（无本地 git 工作区，或 `origin` 已 resolve 到该唯一仓库）→ 直接用该仓，不要向用户追问「改哪个仓库」。
- **必须问仓库**：本项目有**两个及以上**仓库，或本地 remote 无法解析 / 对不上本项目任一仓库 → **停下来**，列出平台仓库名（及 slug）请用户选一个。不要猜，不要擅自改错仓。

### 基线分支（少打断）

- 目标仓确定后，基线默认 = 该仓的 `defaultBranch`。
- **凡向用户说明或确认基线时**，必须附带**本地常见分支**列表：在用户工作区执行 `git branch` / `git branch -a`，至少展示本地已有的 `master` / `main` / `develop`、当前分支，以及与 `defaultBranch` 同名的分支。
- **可不追问、直接采用 `defaultBranch`**：本地存在与 `defaultBranch` 同名的分支（或已检出该分支），且用户未提出异议。
- **要问基线**：本地没有对应分支、同时存在与 default 不符的多个候选（如既有 `main` 又有 `master`），或工作区不在目标仓路径下。

## 推荐修复流程（含 PR）

一个缺陷一条分支、一个 PR；不要把无关缺陷塞进同一个 PR。AI **只提 PR、不合并**；合并由人（项目负责人或有审查权限的开发）在网页完成。

```
┌─────────────┐    ┌─────────────┐    ┌──────────────┐    ┌─────────────┐
│ 1 查缺陷    │───▶│ 2 定仓库    │───▶│ 3 分支上修复 │───▶│ 4 推送+提PR │
└─────────────┘    └─────────────┘    └──────────────┘    └──────┬──────┘
                                                                 │
                                                                 ▼
┌─────────────┐    ┌─────────────┐    ┌──────────────┐    ┌─────────────┐
│ 8 通过/驳回 │◀───│ 7 审核人验证│◀───│ 6【人】合并PR│◀───│ 5 提交修复  │
└─────────────┘    └─────────────┘    └──────────────┘    └─────────────┘
```

步骤说明：

1. `get_defect` / `search_defects` 确认缺陷与状态（须为处理中或已驳回，且你是处理人）。
2. 按上一节定 `repository_id`（单仓且 remote 对得上则不问）。
3. 从基线（默认 `defaultBranch`；说明时列出本地常见分支）建 `fix/defect-<编号>`，改代码、补测试。
4. 推送到平台仓库，创建 PR：源分支 = 修复分支，目标分支 = 基线；描述用可读中文写清 `#编号`、原因与验证方式（少堆英文标识符）。
5. `repair_defect`：关联 `repository_id` + `sha`；默认审核人 = 缺陷创建人（提出 bug 的人），处理人随之变为审核人。**不要把自己设为审核人。**
6. 等人审代码并点「合并」。
7. 审核人在含修复的版本上验证，`pass_defect` 或 `reject_defect`。
8. 驳回后在同一分支继续改并推送，PR 自动更新；修好后再 `repair_defect`。

## 关联提交

1. 推送后取得提交 SHA。
2. 调用 `repair_defect`，`commits` 里传 `repository_id` + `sha`（平台托管仓库会校验提交存在）；代码在外部仓库时传 `sha` + `url`。
3. 汇报「#编号 已提 PR 并提交修复，关联提交 abc1234，进入待审核，由 Y 验证；请有权限的人合并 PR」。

## 使用建议

- 用户在本地仓库里工作时，先用 `resolve_project_by_git_remote` 确认它就是本项目的仓库。
- 本地已有代码时优先读本地文件；需要看其他分支或别人推送的版本时再用平台工具。
- 多个缺陷并行时，每个缺陷独立分支与 PR，便于单独合并或回退。
