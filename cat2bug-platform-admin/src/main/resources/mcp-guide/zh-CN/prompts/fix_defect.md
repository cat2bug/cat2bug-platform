按以下步骤进行，每完成一步用一两句话告诉我结果和下一步：

```
 查询缺陷 → 确认仓库 → 建分支修复 → 推送并提 PR
      → 提交修复(处理人=提缺陷人) → 【人】审代码并合并
      → 【审核人】验证通过/驳回
```

1. 调用 `get_guide(topic=defect)`，了解流转规则和我的权限；需要代码仓库约定时再调 `get_guide(topic=code)`。
2. 用 `get_defect` 读取缺陷详情和处理记录（注意驳回原因和评论）。如果我不是当前处理人，或状态不是处理中 / 已驳回，告诉我当前处理人是谁、状态是什么，并停止。
3. 确认要改哪个源码仓库（规则见 `get_guide(topic=code)`，少打断）：
   - 用 `get_current_project` 或 `list_repositories` 取得仓库列表（含 `defaultBranch`）；本地有工作区时对 `origin` 调 `resolve_project_by_git_remote`。
   - **单仓库**且（无本地仓或 remote 已对上该仓）→ **不问仓库**，直接用它。
   - **多仓库**，或 remote 对不上 / 解析失败 → **必须问我**，列出平台仓库请我选；不要猜。
   - 多个缺陷不要混在同一个分支 / 同一个 PR 里（同一根因可合并，描述里写清所有编号）。
4. 确定基线分支后新建修复分支（建议 `fix/defect-<编号>`）：
   - 基线默认用目标仓 `defaultBranch`；说明或确认基线时，用 `git branch` 列出本地常见分支（`master` / `main` / `develop`、当前分支、与 default 同名的分支）给我看。
   - 本地已有与 `defaultBranch` 同名分支时可直接采用，不必反复追问；本地没有对应分支或多候选不一致时再问我。
   - 说明问题原因和修改方案，经我同意后再改代码；补测试并跑通相关用例。
5. 推送分支到平台仓库，用通用通道创建合并请求（`describe_operation` / `call_operation` → `gitPullRequest.create`）：标题与描述用**可读中文**写清 `#编号`、现象、原因、改了什么、怎么验证；少堆英文方法名 / 字段名，必要时用中文含义，字段名放括号。**不要自行合并 PR**，合并由有审查权限的人在网页完成。
6. 调用 `repair_defect`：写清修复说明，在 `commits` 里关联提交；`review_by` 默认用缺陷创建人（提出 bug 的人）。若创建人就是我自己，或存在多人需改选，用 `list_project_members` 请我指定审核人。提交后缺陷进入待审核，处理人变为审核人。
7. 告诉我：已提 PR、缺陷待审核；代码合并后由审核人验证；若驳回会退回给我，在同一分支继续改，PR 会随推送更新。
