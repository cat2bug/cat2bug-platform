# 权限模型与鉴权链路

说明后端如何用 `@RequiresPermissions` 实现原 Spring Security `@PreAuthorize` 的语义、功能权限如何随「当前团队/项目」变化、数据权限（DataScope）如何生效，以及 Git 仓库 pull / push / manage 的判定矩阵；新增受保护接口、改 Git 权限或排查「没有权限」时参考。

## 概述

- 请求经过三道关卡：**认证**（`JwtAuthFilter`，Open API 走 API Key，Git Smart HTTP 走 Basic，MCP 走 OAuth 访问令牌）→ **功能权限**（`PermissionAuthorizationFilter` + `@RequiresPermissions`）→ 业务层**资源级校验**（如 Git 仓库 ACL，见下文「Git 仓库访问控制」）。
- `@RequiresPermissions` 是原 Spring 线 `@PreAuthorize("@ss.hasPermi('…')")` 的简化等价：可标在类或方法上（方法优先），`value` 为权限串数组，`logical` 默认 `AND`，可选 `OR`。
- 权限串集合来自用户在**当前团队 + 当前项目**下的角色，不是全局固定的；切换项目后会重算。

## 关键流程

1. **认证**（`@Priority(AUTHENTICATION)`）：
   - `/api/**`（`OpenApiPaths`）跳过 JWT，由 `ApiKeyAuthFilter` / `ApiFeaturePermissionFilter` 处理。
   - `PublicPaths`（如 `setup/**`、`upgrade/**`、`q/health`、`websocket/**`、`profile/**`、邀请链接预览等）放行，但若带了有效 Token 仍会解析出登录用户。
   - Git Smart HTTP 路径（`/git/**` 与 `/{teamKey}/{projectKey}/code/{slug}.git/**`）跳过 JWT，改由资源内 HTTP Basic 校验，见 [[Git Smart HTTP与在线浏览]]。
   - 其余路径无登录用户即返回 code=401。
2. **功能权限**（`@Priority(AUTHORIZATION)`）：无注解直接放行；有注解则用 `PermissionChecker` 判定，失败返回 code=403。
3. **`PermissionChecker` 判定规则**：超级管理员（`SysUser.isAdmin(userId)`、角色 `isAdmin()` 或 roleKey 为 `admin`）恒为真；否则看权限集合是否含 `*:*:*` 或目标权限串。
4. **权限集合来源**：`SysPermissionService.getMenuPermission` 汇总角色对应的菜单 `perms`；角色由 `SysRoleService.selectRolesByUserId` 按 `sys_user_config` 的 `current_team_id` / `current_project_id` 调 `selectRolePermissionByUserId(teamId, projectId, userId)` 求并集。
5. **何时重算**：`DefaultLoginUserPermissionEnricher` 在会话未合并过上下文权限时懒加载；用户切换团队/项目（`UserConfigResource`）时调用 `updateRoleAndPermissionOfCurrentUser` 重算并写回会话（`TokenService.updateLoginUser`）。
6. **数据范围**（见下文「数据权限」）：`PermissionAuthorizationFilter` 校验通过后把注解上的权限串（逗号连接）写入请求级 `AuthContext.permissionContext`，供数据范围按权限字符筛选角色。
7. **会话存储**：`SessionStore` 支持内存与 Redis（`cat2bug.session.store`，默认 `auto`，配置了 `cat2bug.redis.hosts` 时使用 Redis）。

| 12 | `team.create-by` | 团队创建人 |
| 6 | `project.admin` | 项目管理员 |

### 数据权限（DataScope）

对齐原 Spring 线 `DataScopeAspect#dataScopeFilter`，只作用于**用户、部门**两类数据；超级管理员（`SysUser.isAdmin()`）不过滤。

- 生成：`DataScopeSqlBuilder`（`cat2bug-platform-system/.../system/security/`）按当前登录用户的角色生成 ` AND (...)` 片段：

  | data_scope | 含义 | 条件 |
  |---|---|---|
  | `1` | 全部 | 不加条件（任一角色为 `1` 即整体不过滤） |
  | `2` | 自定义 | `d.dept_id IN (SELECT dept_id FROM sys_role_dept WHERE role_id = ?)` |
  | `3` | 本部门 | `d.dept_id = 用户部门` |
  | `4` | 本部门及以下 | `CONCAT(',', ancestors, ',') LIKE '%,部门ID,%'`（不用 `find_in_set`，H2 没有） |
  | `5` | 仅本人 | `u.user_id = 用户ID`；没有用户表别名（部门列表）时不匹配任何数据 |

  多角色取并集；角色的菜单权限（登录时记入 `SysRole.permissions`）不含本次接口任何一个权限串时，该角色不参与（`*:*:*` 视为都含）；没有可用角色或用户无部门时条件为 `d.dept_id = 0`（查不到数据）。
- 传递：片段作为 Mapper 的**独立参数** `@Param("dataScope")`，XML 用 `${dataScope}` 拼接，不经实体 `params`，请求参数无法注入。片段只包含数字 ID 和经正则校验的常量表别名。
- 生效位置：`SysUserMapper.xml` 的 `selectUserListWhere` / `allocatedListWhere` / `unallocatedListWhere`（用户列表、角色已分配 / 未分配用户、用户导出），`SysDeptMapper.xml#selectDeptList`（部门列表、部门树、排除子部门）。
- 单条校验：`SysUserService.checkUserDataScope`（详情、修改、删除、重置密码、改状态、分配角色、导入覆盖）、`SysDeptService.checkDeptDataScope`（详情、修改、删除），目标不在范围内抛「没有权限访问用户数据！」/「没有权限访问部门数据！」。
- 角色来源：使用会话里当前生效的角色（`user.roles`，按当前团队 / 项目求并集）。用户还没有 `sys_user_config`（未选团队 / 项目）时，`user.roles` 改用 `sys_user_role` 中启用的系统角色，与此时菜单权限的来源一致。
- **角色列表不过滤**：原 Spring 线 `SysRoleMapper.xml` 里的 `${params.dataScope}` 本就被注释；团队 / 项目角色没有部门归属，过滤会把它们全部藏掉。`checkRoleDataScope` 只校验角色存在。

### Git 仓库访问控制

判定入口 `GitRepositoryAccessService`（实现 `GitRepositoryAccessServiceImpl`）提供 `canPull` / `canPush` / `canManage` / `resolveEffectiveRole` / `isSystemAdmin`，Smart HTTP、在线浏览、分支/标签/设置等接口共用。`evaluate(userId, repositoryId)` 顺序：

1. `userId` 或 `repositoryId` 为空 → 拒绝。
2. **系统管理员**（`isSystemAdmin`：`SysUser.isAdmin(userId)`，或任一角色 roleKey 为 `admin`）→ 仓库存在则全权限，不存在则拒绝。
3. **仓库 ACL**（`sys_git_repository_member` 中该用户的行）存在 → 按 ACL 角色，且**不再与项目角色合并**（可用 ACL 把项目管理员降为只读）：

   | ACL 角色 | pull | push | manage（含 force-push） |
   |---|---|---|---|
   | `admin` | ✓ | ✓ | ✓ |
   | `write` | ✓ | ✓ | |
   | `read` | ✓ | | |

4. 无 ACL → 查用户在仓库所属项目下的角色（`selectRolePermissionByUserId(null, projectId, userId)`，不传 teamId）：`project.create-by` / `project.admin` 等效 `admin`；`project.develop` / `project.tester` 等效 `write`；其他拒绝。

`SysGitRepositoryServiceImpl.matchesAnyRole(projectId, userId, roleIds)` 用于「按项目」的仓库操作（创建、导入、列表等）：系统管理员直接放行；否则看项目角色 ID 是否落在 `MANAGE_ROLE_IDS = {6, 11}` 或 `READ_WRITE_ROLE_IDS = {7, 8}`（读写与管理取并集）。`assertManage` / `assertPull` 按项目判定，`assertRepoPull` / `assertRepoManage` 委托给 `GitRepositoryAccessService`。

### OAuth 访问令牌（MCP）

AI 客户端以**用户本人**身份接入：只填 MCP 地址，在浏览器用账号密码登录并选团队、项目，**一次授权绑定一个项目**。令牌只在 MCP 路径（`/mcp`、`/mcp/*`）生效，在 `/system/**` 等网页接口上无效（`JwtAuthFilter` 不认这类令牌）。没有个人访问令牌（`c2b_pat_` 已删除）。决策见 [[ADR-016-AI客户端只经OAuth登录接入且授权绑定单个项目]]（取代 [[ADR-013-AI客户端以个人身份接入-个人令牌加自带OAuth]] 的个人令牌部分）。

- **一张表** `sys_user_access_token`（`source`：`oauth` 访问令牌 / `oauth_refresh` 刷新令牌；`project_id` 为授权项目）。只存 SHA-256 哈希与展示前缀。前缀：`c2b_oat_`（OAuth 访问）、`c2b_ort_`（刷新）、`c2b_oac_`（授权码，存 `sys_oauth_code`）；动态注册的 client_id 为 `c2b_client_…`（`sys_oauth_client`）。
- **鉴权**：Quarkus Security 的 `AccessTokenAuthMechanism` + `IdentityProvider`（不是 JAX-RS Filter，MCP 端点走 Vert.x 路由），校验存在、`source=oauth`、带 `project_id`、未过期、未吊销、用户未停用 / 未删除，`LoginUser` 与授权项目分别放在 identity 属性 `cat2bug.loginUser`、`cat2bug.projectId`，用 `AccessTokenIdentities.loginUser(identity)` / `projectId(identity)` 取。失败一律 HTTP 401，不区分原因。`quarkus.http.auth.permission.mcp` 要求 MCP 路径已认证。
- **OAuth 2.1 最小授权服务器**：元数据 `/.well-known/oauth-authorization-server`；`/oauth/register`（RFC 7591，只收公开客户端，redirect_uri 须 https 或回环地址）；`/oauth/authorize` 校验后 302 到前端确认页 `/oauth/consent`；确认页 `check` 返回按团队分组的可选项目（本人是成员且已开启 MCP；系统管理员可选全部已开启 MCP 的项目），用户选项目并允许后 `/oauth/authorize/decision`（JWT，须带 `project_id`，不在可选列表内即拒绝）发授权码（10 分钟、一次性、带项目）；`/oauth/token` 授权码 + PKCE S256 换访问令牌（1 小时）与刷新令牌（30 天），新令牌沿用授权码 / 旧令牌的 `project_id`，刷新时轮换，旧刷新令牌重放则按 `grant_id` 吊销整条链；`/oauth/revoke`。
- **对外地址**：issuer、MCP 地址优先取 `cat2bug.public-url`，未配置时按 `X-Forwarded-Proto` / `X-Forwarded-Host` / `Host` 推导（`PublicUrlResolver`），见 [[部署]]。
- **防滥用**：register / token / revoke 按 IP 限流（`IpRateLimiter.clientKey`：只有直连地址是回环 / 内网时才信任 `X-Forwarded-For` 最后一段，公网直连用连接地址）；确认页禁止被 iframe 嵌入（前端检测 + `X-Frame-Options` / `frame-ancestors` 响应头）；decision 只认请求头里的 JWT，不读 Cookie，无 CSRF 面。
- **令牌能做什么**：只能操作**授权项目**，等同用户本人在该项目中的角色权限，再与项目 MCP 设置勾选的模块求交集；系统级权限不开放；按（用户，项目）单独计算，不改 `sys_user_config` 当前项目。MCP 工具经回环网关以短时内部会话（`operChannel=mcp`，只接受回环来源）调用网页接口。详见 [[MCP接入与权限]]、[[ADR-014-MCP权限为角色权限与项目模块的交集]]。

## 注意事项

- **数据权限**：新增用户 / 部门相关查询时，要把 `dataScopeSqlBuilder.forCurrentUser(...)` 的结果作为 `dataScope` 参数传给 Mapper，并在 XML 末尾拼 `${dataScope}`；**不要**把它放进实体 `params`，也不要拼接任何来自请求的字符串。数据范围受限的角色看到的用户 / 部门列表会比 2026-10 之前少，这是预期行为。
- 功能权限依赖「当前项目」上下文：跨项目操作（直接带别的 `projectId` 调接口）只靠 `@RequiresPermissions` 不够，业务层要按目标项目再校验角色——Git 仓库就是这样做的。
- Git 浏览类接口同时挂 `@RequiresPermissions("system:git:repo:pull|manage")` 与服务层仓库级校验，两者都要通过。
- 项目角色 ID 在 `SysGitRepositoryServiceImpl` 中**硬编码**（6/7/8/11），`GitRepositoryAccessServiceImpl` 则按 roleKey 判定；改角色初始化数据时两处都要核对。
- 认证/授权失败是 HTTP 200 + JSON code，见 [[分页与统一响应]]；Git Smart HTTP 例外，返回真实 401/403。

## 待确认

- 团队 / 项目角色的 `data_scope` 初始化为 `1`（全部）。用户在团队上下文中持有带用户列表相关权限（如 `system:team:member:invite`）的团队角色时，数据范围等同全部；是否需要按团队收窄待确认。
- 仓库字段 `visibility`（`public`「开源：所有人可见」/ `project`）只做存储与规范化，`GitRepositoryAccessServiceImpl` 判定时没有读取它，`public` 对非项目成员的实际放行范围需确认。
