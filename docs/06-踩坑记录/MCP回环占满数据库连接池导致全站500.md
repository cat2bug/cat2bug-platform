# MCP 回环占满数据库连接池导致全站 500

- 日期：2026-10-18
- 涉及：后台（MCP / 数据库连接池）

## 现象

Cursor 里的 Cat2Bug MCP 在并行调用 `update_plan_item` 后变成 Not connected。`https://cloud.cat2bug.com/mcp` 的 `POST /mcp` 返回 HTTP 500，正文是 `{"msg":"服务器内部错误","code":500}`。随后 SSE 也是 500，客户端只重连两次就停住。同一时段网页接口只要要查库，也会失败。

## 根因

`runtime-mysql` 连接池默认只有 20，MCP 回环在途上限只按工作线程推算（约 66）。每条在途回环的内层请求都要占一条 JDBC 连接。并行改同一测试计划的子项时，`updateSysPlanItem` 在一个事务里再更新计划行的 `update_time`，这些事务排队等同一把行锁，连接会一直占到 `innodb_lock_wait_timeout`（云站为 50 秒）。

池被占满后，新的 MCP 请求在 `AccessTokenIdentityProvider` 里查 `SysUserAccessTokenMapper.selectByHash` 就拿不到连接，Agroal 抛 `Sorry, acquisition timeout!`。这是未处理异常，变成 HTTP 500。Cursor 把非 2xx 当成传输故障，拆掉会话。网页和其它 API 走的是同一个池，所以会一起失败。MySQL 的 `max_connections` 当时远没有用满。

## 解决办法

- `quarkus.datasource.runtime-mysql.jdbc.max-size` 改为 40。
- 回环在途数默认改为 `min(max(4, 线程池/3), 连接池的一半)`，多余的工具调用返回「系统繁忙」，不再把池借光。
- 同一计划 2 秒内只刷新一次 `update_time`，避免并行改子项时抢同一行。
- 连接池耗尽时返回 HTTP 503「系统繁忙，请稍后重试」，不再伪装成未处理的 500。MCP 路径上只要还是非 2xx，Cursor 仍会拆会话，所以关键是不要让池被占满。

云站要重新部署后端镜像后才生效。运行中的容器不会自己读到仓库里的新默认值。

## 以后怎么避免

- 新增会占着连接等待的 MCP 路径时，在途数必须小于 `runtime-mysql` 的 `max-size`，并给令牌校验和网页留出一半。
- 不要在高并发事务里反复更新同一行。计划的「最近更新时间」用短间隔合并即可。
- 显式配置 `cat2bug.mcp.loopback.max-in-flight` 时，不要大于连接池的一半。
