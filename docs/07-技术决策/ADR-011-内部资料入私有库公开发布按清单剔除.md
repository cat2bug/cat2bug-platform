# ADR-011 内部资料入私有库，公开发布按清单剔除

记录 `docs/`、`openspec/` 等内部资料与开源发布之间如何划边界。

- 日期：2026-10-14
- 状态：已采纳

## 背景

仓库有三个远端：`private-gitee`（私有，`core` 的默认上游）、`github` 与 `public-gitee`（公开）。此前内部资料与开源发布没有边界：`docs/` 知识库被 `.gitignore` 忽略，连私有库都进不去，只存在于本机；而 `openspec/`、`readme/` 的内部计划又会随 `core` 一起推到公开库。依据：`openspec/changes/retire-spring-and-unify-modules/design.md`（D5、D6）。

## 候选方案

### 方案 A：每次发布用 `git filter-repo` 全量重写

缺点：慢，且每次都会改写公开历史。否决。

### 方案 B：`git subtree split`

缺点：只能按单个目录拆分，无法表达「整仓减去若干目录」。否决。

### 方案 C：内部资料照常提交到私有库，发布时用临时索引生成一个剔除内部路径的提交

优点：不改工作区、不改写历史；公开分支是一串增量提交，可以直接推送。

缺点：公开历史与 `core` 历史不是同一条线，公开库看不到逐个开发提交；清单要人工维护。

## 最终决定

采用方案 C：

- `.gitignore` 删除 `/docs/` 规则（保留 `docs/.obsidian/workspace*` 等个人文件的忽略），`docs/`、`openspec/`、`readme/` 内部部分照常提交到 `private-gitee`。
- `.cursor/`、`.claude/`、`.github/`、`assets/`、`CLAUDE.md` 维持不入库；不改写历史，它们在历史中出现过的版本保留原样。
- 清单 `deploy/public-release-exclude.txt` 列出不公开路径，当前为 `docs/`、`openspec/`、`readme/core/`、`readme/development/skills/_sources/`；`readme/production` 等用户文档保持公开。
- 脚本 `deploy/scripts/export-public.sh` 的做法：
  - 基于 `core` HEAD 的树，用临时索引（`GIT_INDEX_FILE`）`read-tree`，再 `rm --cached` 清单路径。
  - `write-tree` + `commit-tree` 生成提交，父提交为本地分支 `public/master` 的上一次导出（首次为 `github/master`），然后更新 `public/master`。
  - 树级自检：导出提交的树中不能包含清单里的任何路径。
  - 不改工作区、不推送，只打印推送命令，由人工执行。
- 提交 `63dc1a4f`。

## 原因

- 知识库和 OpenSpec 是团队与 AI 的长期上下文，必须进版本库，至少进私有库才能共享和备份。
- 公开发布只需要「整仓减去内部目录」的快照，临时索引方案最简单，也不碰历史。

## 副作用

- 新增内部目录时必须同步更新 `deploy/public-release-exclude.txt`，否则会随下次导出公开；首次导出后要人工核对 `git show --stat`。
- 推送公开库前必须先跑导出脚本，不能直接把 `core` 推到 `github` / `public-gitee`。
- `docs/` 入库后，文档里**不能**写真实密码、Token 或私有地址（私有库也一样）。
