# ADR-014 MCP 权限 = 用户在项目的角色权限 ∩ 项目开放的 MCP 模块，系统级操作不开放

约束以后所有 MCP 工具与通用通道的授权方式；新增给 AI 用的能力也按此计算权限。

- 日期：2026-10-15
- 状态：已采纳

## 背景

[[ADR-013-AI客户端以个人身份接入-个人令牌加自带OAuth]] 确定了 AI 以用户本人身份接入、令牌不带独立权限范围。还需要决定：AI 能做的事是否等同用户在网页上能做的事；项目管理员能否收窄；系统管理类操作是否开放。另外网页的功能权限按用户「当前项目」（`sys_user_config`）计算，AI 同时操作别的项目时不能借用这套机制。依据：`openspec/changes/mcp-server/design.md` D1～D3。

## 候选方案

### 方案 A：令牌自带权限范围（scope）

优点：用户可以给不同客户端发不同权限的令牌。

缺点：多一套权限模型要维护和展示；与角色体系不一致，容易出现「网页不能做、AI 能做」。

### 方案 B：完全等同用户网页权限

优点：最简单。

缺点：项目管理员无法关闭某些模块（例如不希望 AI 碰报告或代码）；系统管理员令牌泄露的影响面过大。

### 方案 C：角色权限 ∩ 项目 MCP 模块勾选，系统级前缀固定排除

优点：只有一套权限逻辑（角色），项目可收窄，系统级操作从机制上不可达。

缺点：模块与权限前缀的映射表需要随菜单权限维护。

## 最终决定

采用方案 C：

- 项目设置 `sys_project_mcp`：开关 + 已勾选模块列表；没有记录即关闭（老项目升级后默认关闭），新建项目默认开启并全选；存「已勾选」而非「已排除」，新模块对已有项目默认不开放。
- 模块到权限前缀的映射在 `McpModules`；不在映射内的权限（用户、角色、菜单、字典、团队、项目 API Key、新建 / 删除 / 推送项目等）一律不开放。
- 勾选只是开关，读写能力仍由角色决定。
- 有效权限按（用户，目标项目）单独计算，不读写 `sys_user_config`，AI 操作不切换网页当前项目。

## 原因

- 「AI 能做的 ≤ 本人在网页上能做的」是最容易解释、也最不容易出错的边界。
- 项目级开关满足「有些项目不允许接 AI」的诉求，又不引入第二套权限。
- 系统级操作极少需要 AI 代劳，固定排除可避免管理员令牌泄露后被用于改用户、改角色。

## 副作用

- 新增项目内权限串时，要确认它的前缀落在 `McpModules` 某个模块里，否则 MCP 中不可用；新增系统级权限不要用项目模块的前缀。
- 有效权限缓存 30 秒，成员角色变更最多延迟 30 秒在 MCP 中生效。
- 实现见 [[MCP接入与权限]]；网页侧权限模型见 [[权限模型与鉴权链路]]。
