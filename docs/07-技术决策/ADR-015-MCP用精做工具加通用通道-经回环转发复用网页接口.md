# ADR-015 MCP 采用「精做工具 + 通用通道」，两者都经回环转发复用网页接口

约束以后给 MCP 增加能力的方式：高频场景做精做工具，其余靠通用通道；都不直接调 Service、不另写权限判断。

- 日期：2026-10-15
- 状态：已采纳

## 背景

项目内接口有数百个，AI 需要覆盖网页上能做的大部分事，同时高频闭环（读缺陷 → 修复并关联提交 → 通过 / 驳回）要调用准确。网页接口的权限、数据范围、分页、操作日志、异常映射都在 JAX-RS 过滤器链上，若 MCP 另调 Service，就要把这些再写一遍。依据：`openspec/changes/mcp-server/design.md` D6～D7。

## 候选方案

### 方案 A：每个接口生成一个 MCP 工具

优点：覆盖全，自动生成。

缺点：几百个工具挤满模型上下文，选错工具概率高，部分客户端限制工具数量。

### 方案 B：精做工具直接调用 Service

优点：没有 HTTP 开销。

缺点：绕过过滤器链，权限、日志、数据范围要重写，形成两套逻辑。

### 方案 C：少量精做工具 + `list_operations` / `describe_operation` / `call_operation` 通用通道，全部经回环 HTTP 转发到原接口

优点：只有一套权限与日志；工具数量可控（约 35 个）；新接口自动进入通用通道。

缺点：多一次本机 HTTP；需要内部会话；需要在 MCP 层补对象归属校验。

## 最终决定

采用方案 C：

- 每次调用创建 120 秒的内部会话（角色、权限按目标项目计算，带 `operChannel=mcp` 与客户端名），对 `127.0.0.1` 发起请求，结束即删除；内部会话只接受回环来源，不能经 Cookie 使用。
- 通用通道的操作目录由启动时扫描 JAX-RS 资源生成，只收录权限落在已开放模块、返回 JSON 的接口，排除导入导出、上传下载、Git Smart HTTP 及读 `sys_user_config` 当前项目的接口。
- 网页接口按 ID 访问时不校验对象所属项目（既有问题），MCP 层转发前必须校验所有对象 ID 属于目标项目，不认识的 ID 字段拒绝。

## 原因

- 权限和审计只有一份，网页规则变了 MCP 自动跟随。
- 精做工具负责「好用」，通用通道负责「够全」，两者分工让工具数量保持在模型能稳定选择的范围。

## 副作用

- 新增或修改项目内接口时：若引入新的对象 ID 参数，要在 `McpOperationCatalog.OWNED_PARAMS` / `McpObjects` 补归属校验；若接口从 `sys_user_config` 读当前项目，要加入排除清单。
- 回环地址默认 `127.0.0.1:{quarkus.http.port}`，只监听特定地址或端口特殊的部署要配置 `cat2bug.mcp.loopback-url`。
- Native 需要为 `com.cat2bug.admin.resource.` 注册反射，操作目录才能读取注解。
- 实现见 [[MCP接入与权限]]。
