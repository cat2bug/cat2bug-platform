# ADR-025：Flyway 迁移版本与产品版本对齐

- 日期：2026-11-04
- 状态：已采纳

## 背景

产品版本（`pom` / `cat2bug.version`，升级页「当前/目标版本」）已升到 `1.2.1`，而 Flyway 脚本长期沿用 `V1_1_0_N` 序号线，升级向导上会出现「产品 1.2.1、待迁移 1.1.0.x」两套编号，易误解为漏发版或脚本过期。

## 候选方案

### 方案 A：继续只递增 `1.1.0.N`

优点：与历史库、踩坑记录完全一致，无改名成本。

缺点：与产品版本永久脱节。

### 方案 B：自当前产品版起，新脚本用 `V{maj}_{min}_{patch}_{seq}`

优点：升级页上待迁移版本与产品版本同一语义前缀；历史已应用脚本不动。

缺点：需记住「同产品三段版本内 seq 递增」；旧 `V1_1_0_*` 仍留在历史中。

### 方案 C：回溯改名全部已发布脚本

优点：表面完全统一。

缺点：已写入 `sys_db_version` 的版本不可改名（校验和/版本冲突），所有存量库会炸。不可行。

## 最终决定

采用方案 B。

1. **历史**：已发布的 `V1_1_0_*`（及更早）永不改名、不改内容。
2. **自产品 `1.2.1` 起**：新迁移命名为 `V1_2_1_{seq}__描述.sql`（MySQL / H2 成对），`seq` 从 `1` 起在同一产品三段版本内递增。
3. **产品升版**（如 `1.2.1` → `1.2.2`）：该版本上第一条新迁移用 `V1_2_2_1`，序号重新从 1 起。
4. **未入库脚本可改名**：尚未写入任何环境 `sys_db_version` 的待发布脚本，可在合入前改到新规则（本变更将原拟定的 `1.1.0.60/61` 改为 `1.2.1.1/2`）。

## 原因

两套编号只需在「可改」范围内对齐；强行改历史会破坏升级路径。产品三段 + 段内序号既对齐发版语义，又保留 Flyway 单调递增能力（`1.2.1.2` > `1.1.0.59`）。

## 副作用

- 取「下一版本号」时：先看当前产品 `major.minor.patch`，再查同前缀下最大 `seq`，而不是全局 `1.1.0` 最大号 +1。
- 仍须扫描未合并分支与开发库，避免同版本号撞车（见 [[Flyway版本号冲突与乱序补跑]]）。
- `outOfOrder` 继续开启；乱序补跑脚本仍须幂等。
